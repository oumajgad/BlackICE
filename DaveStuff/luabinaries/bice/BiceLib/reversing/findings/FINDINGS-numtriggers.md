# The numeric and comparison triggers: what is read, against what, and in what units

`findings/FINDINGS-triggereval.md` read the machinery — slot 6 is `Evaluate`, there is no cache, and
the four composites walk a child list. This is the content: the 78 leaves whose slot 6 is one
numeric comparison, and the three different scales their operands are on.

Addresses are **rvas** against an image base of `0x400000`, as everywhere in this folder.

## 1. The answer in one paragraph

A leaf trigger's operand does not come from its own `LoadKey`. `CTrigger::LoadKey` builds the leaf,
appends it to the parent's child list, copies the 0x104-byte `CToken` at `CParseContext::value`
(`+0x228`) onto the stack and calls **slot 7** on the new object (`call [vftable+0x1C]` at
`0x5C8E6F`). Slot 7 is where the units are decided, and there are **five bodies of it**, one per
operand kind:

| slot 7 | rva | holders | what it writes |
| --- | --- | --- | --- |
| `CValueTrigger` | `0x5D13E0` | 40 | `TokenToFixedPoint` → `+0x40`, **thousandths** |
| `CIntTrigger` | `0x5D1400` | 37 | `atoi` → `+0x40`, **raw**; or the `this`/`from` flags |
| `CBoolTrigger` | `0x5D1480` | 26 | `(token == 0x1F6 /* yes */)` → `+0x40` as a byte |
| `CStringTrigger` | `0x5D1450` | 10 | `assign(text, strlen)` → the `Hoi3CString` at `+0x40` |
| `CTagTrigger` | `0x5E8F40` | 16 | `CCountryDataBase::GetTag` → `+0x40`/`+0x44`, or the flags |

`CTrigger`'s own slot 7 is rva **`0x15FF0`** — the empty `ret 0x104` that `project.json` already
records as `CEffect::TakeScalarValue`, with the comment "**Slot 7: what an effect written as
`keyword = value` does with that value**". The trigger side and the effect side share one folded
stub at the same slot index, so that record was already describing both halves of the language.

So the whole units question reduces to **which of the five slot-7 bodies a leaf's base gives it**,
and then to whether its `Evaluate` scales either side. There are only four possibilities, and the
instruction count of the body is usually enough to tell them apart:

1. **`CValueTrigger`, no scaling in the body** (17 instructions) — the field is thousandths and the
   script number is the number the savegame prints. 13 leaves.
2. **`CValueTrigger`, operand divided by 1000** (25 instructions, `mov eax,0x10624DD3; imul ecx`) —
   the field is a whole number and the script number is a plain count. 10 leaves.
3. **`CIntTrigger`, no scaling** — field and operand are both plain integers. 20-odd leaves.
4. **`CIntTrigger`, operand multiplied by 1000** (`imul reg,reg,0x3e8`) — the field is thousandths
   and the script number is the natural unit, but it **cannot carry decimals**, because `atoi` has
   already truncated them. 4 leaves.

Plus two one-offs: `CBuildingTrigger` divides the **field** by 1000 with the same magic, and
`CThreatTrigger`/`CRelationTrigger`/`CAllOrganisationPopularityTrigger` keep their own value at
`+0x48`, parsed by their own `LoadKey` with plain `atoi`, and multiply by 1000 in `Evaluate`.

**Which side the 0x10624DD3 divide applies to has to be read off the instruction.** A scan that
only asks "does this body contain the divide-by-1000 magic" puts `CBuildingTrigger` in the same
bucket as `CTotalICTrigger`, and they are opposites.

## 2. `TokenToFixedPoint` was already in the record, and that is the control

Rva `0x669550` is already recorded as `TokenToFixedPoint`, `confirmed`, with its semantics spelled
out: `*out = atoi(text) * 1000 + fraction`, the fraction padded to exactly three places, and the
`__allmul`/`__alldiv` round trip identified as a 64-bit overflow guard rather than a second scaling.
I read it end to end before grepping for it, got the same answer, and found the record already
holding it — so **this section is an independent agreement, not a settlement** (trap 14, and the
check that `project.json` is only half the fact base paid for itself twice in this pass).

The savegame is the second control and it is decisive, because **the save's own writer makes the
same distinction the two trigger bases make**. In `Ireland1945_01_22_02.hoi3`:

- `war_exhaustion=7570.000`, `dissent=0.000`, `national_unity=81.752`, `neutrality=88.800`,
  `manpower=271.460`, `spies=1930.792` — three decimals, i.e. thousandths, and every one of those
  keys is read by a `CValueTrigger` leaf with no scaling in its body.
- `land_battles_fought=301`, `air_battles_fought=7`, `naval_battles_fought=262` — no decimal point
  at all, and all three are read by `CIntTrigger` leaves with no scaling.

Two writers, two scales, matching the two bases key for key. That is as close to a machine check as
this question gets.

## 4. What a mod author gets wrong because of this

Each of these is read off the bytes, not inferred from behaviour.

**`manpower_percentage` and `revolt_percentage` are fractions, not percentages.** Both compute
`numerator * 1000 / denominator` out of two thousandths (or two count) fields, so the thousandths
cancel and the left side is the ratio in per-mille; the right side is the script number times 1000.
The condition is therefore `ratio >= <script number>` with the ratio in `0..1`. So
`manpower_percentage = 0.5` is half and `manpower_percentage = 50` demands fifty times the
country's own manpower ceiling, which is unreachable. Same for `revolt_percentage = 0.3`.

**`enemy_ic_ratio` is the only numeric trigger in the family that tests `<=`.** Four `setle`
(`0f 9e`, not `0f 9d`). It is `my max_ic / Σ(enemies' max_ic) <= <script number>`, false for a
country not at war, and false outright if any enemy has `max_ic == 0`. So it reads as "am I
outmatched by at most this ratio".

**`surrender_progress` is on a 0..100 scale.** `CCountry::GetSurrenderProgress` (rva `0xFCB80`)
answers a value clamped to `0..1000`, and the trigger compares `progress * 100` against
`<script> * 1000`, i.e. `progress / 10 >= <script>`. BlackICE writes both `surrender_progress = 80`
(meaningful) and `surrender_progress = 0.05` (satisfied by `progress >= 1` out of 1000, i.e.
essentially always). **The direction is not established**: the function's answer rises with
`national_unity` and its "no data" arm returns the maximum, which reads as "how far from
surrendering", so even `= 80` may not mean what it looks like. Worth a live check.

**`neutrality` and `base_neutrality` are the other way round from their names.**
`CNeutralityTrigger` reads `+0xA90`, which `project.json` already calls `effective_neutrality`
("Neutrality minus the threat the country feels from one single country, floored at zero and capped
at 100000"). `CBaseNeutralityTrigger` reads the raw `+0xA8C`. The same save has Ireland at
`neutrality=88.800` and `effective_neutrality=0.000`, so the two keywords can disagree completely.

**`max_manpower_greater_than` tests current manpower.** Its slot 6 is the *same body* as
`CManpowerTrigger`'s (`0x5EFC20`, `vtable.py --holding` prints exactly two tables), and that body
reads `+0xBCC`. The two classes are siblings under `CValueTrigger`, not one derived from the other,
so this is a linker fold of two identical source bodies — the keyword has never read `+0xBD0`.

**`always = no` is a trigger that is always false, and so is `always = 1`.**
`CBoolTrigger`'s slot 7 is `(token == 0x1F6 /* yes */)`, so anything that is not literally `yes`
stores 0, and `CAlwaysTrigger::Evaluate` is two instructions: `mov al,[ecx+0x40]; ret 4`.

**`check_variable` creates the variable it cannot find, and compares with `>=`.**
`CVariableTrigger::Evaluate` asks `CVariables` slot 1 for the name at `+0x40`; on a miss it calls
`0x76FB0(&name, 0)` and then evaluates `0 >= value`. So a condition on a never-set variable is true
whenever `value <= 0`, and it has a side effect. The threshold at `+0x5C` goes through
`TokenToFixedPoint` (`CVariableTrigger::LoadKey` at `0x5F02B4`), so it is thousandths — matching the
save, which writes variables as `BaseIC=35.000`.

**`total_amount_of_brigades` excludes HQ brigades.** It counts every regiment of every land unit
whose `definition->type_index` differs from `g_CSubUnitDataBase->hq_brigade (+0x78)->type_index`.
All four field names in that chain were already in `project.json` and all four fit.

**`keyword = this` and `keyword = from` are accepted by 37 int triggers and honoured by 3.**
`CIntTrigger`'s slot 7 sets `CTrigger +0x18`/`+0x19` and zeroes the value; only
`CNumOfCitiesTrigger`, `CSubUnitTrigger` and `CUnitsInProvinceTrigger` read the flags back. For the
other 34 the condition degenerates to `field >= 0`.

**`threat`, `relation` and the all-organisation `popularity` cannot take decimals.** They keep their
own value at `+0x48`, parsed by their own `LoadKey` with plain `atoi` (`0x5F2D0A`, `0x5DDF32`,
`0x5FA77E`), and multiply by 1000 in `Evaluate`. So `threat = 50` is fifty and `threat = 50.5` is
fifty.

## 5. `CEventScope +0x40` is the combatant

`findings/FINDINGS-triggereval.md` left `+0x40` open: "the constructor's one stack argument, 0 at 28
of 29 call sites". A scan of all 168 slot-6 bodies for reads through the register loaded from
`[ebp+8]` finds **fifteen** bodies dereferencing `scope->+0x40`, every one of them in the combat
cluster, and three of them are already recorded by name as reading it as the `CCombatant`
(`CCombatModifierTrigger`, `CCombatIsConvoyTrigger`, `CCombatIsWinnerTrigger`) — which is the
positive control. The twelve the record did not have are `CIsAttackerTrigger`,
`CFrontageFullTrigger`, `CReservesTrigger`, `CSkillTrigger`, `CSkillAdvantageTrigger`,
`CTraitTrigger`, `CEnemyScopeTrigger`, `CCombinedArmsTrigger`, `CHasCombinedArmsBonus`,
`CCombatTerrainTrigger`, `CCombatTemperatureTrigger` and `CCombatHasArmourUnitTrigger`.

So a `has_combat_modifier`, `is_attacker`, `skill`, `skill_advantage`, `trait`, `terrain`,
`province_temperature`, `reserves`, `frontage_full`, `has_combined_arms` or `has_armour_unit`
condition is only meaningful inside a scope raised with a combatant — a combat tactic or a combat
mean-time-to-happen — and reads a null pointer anywhere else. That is the 28-of-29 zero the earlier
survey saw: the ordinary event path passes none.

*Wave 12's agent B reached the same name independently, from the scope side rather than from a scan
of the leaves — see `findings/FINDINGS-scopetriggers.md` §7, which is also where the field is
recorded. Two agents, two methods, one answer: corroboration, not a collision.*

## 6. `CCountry +0xF50` closes an open item in another file

`findings/FINDINGS-aiconsumer.md` section 8 lists `CCountry +0xF50` as unknown — "an int slot 73
tests `> 0` as an alternative to `at_war`". Two triggers read it: `CNumOfRevoltsTrigger` as
`num_of_revolts`, and `CNumOfRevoltsFractionTrigger` as the numerator of `revolt_percentage` over
`NumberOfOwnedProvinces (+0xCF8)`. It is a count of provinces in revolt, and the AI's test is "am I
fighting rebels".

## 7. Traps hit in this pass

**Trap 2, five times, and three of them would have put a wrong extent in the record.**

- `0x5F3E90` (`CAmountOfBrigadesTrigger::Evaluate`) — **zero** padding above it; the preceding
  function ends `ret 0x10` at `0x5F3E8D` and this prologue is the next byte, so
  `functionStart` answers `CAmountOfDivisionsTrigger::Evaluate` at `0x5F36E0` with two `ret`s in
  between.
- `0x5D1400` (`CIntTrigger`'s slot 7) — abuts `CValueTrigger`'s slot 7 at `0x5D13E0` with no
  padding.
- `0x669550` (`TokenToFixedPoint`) — a tiny 8-byte function begins at `0x669630`, immediately after
  its `ret 8`, with no padding.
- `0x607980` (`CEnemyScopeTrigger::Evaluate`) and `0x607A00` (`CCombinedArmsTrigger::Evaluate`) —
  two `int3` between them, so a decode that stops only at a run of three runs straight through and
  attributes the second body's field reads to the first. My first `+0x40` scan did exactly that and
  the result had to be thrown away.

**The three-`int3` rule is sufficient, not necessary, and two cases show both failure modes.**
`CSurrenderProgressTrigger::Evaluate` ends at `0x5F826D` with **two** int3 before slot 8 at
`0x5F8270`; a three-int3 walk runs 0x460 bytes past the end into a body that ends `ret 0x10`.
`CRulingPopularityTrigger::Evaluate` at `0x5F9EF0` has **one** int3 above it and
`CEnemyIcRatioTrigger::Evaluate` at `0x608070` has two, and both are genuine entries. What settles
all of them cheaply is the vftable: an address a table holds is an entry point by definition, and
slot 8 gives the upper bound for free. The `ret` immediate is the other cheap check — a `ret 4` and
a `ret 0x10` cannot be one `__thiscall`.

**A new byte for `functionStart`'s prologue set.** `functionStart(0x5D3920)` answers `0x5D38C0`
although the padding there is clean (six int3), because `CAlwaysTrigger::Evaluate` opens with
`0x8A` — `mov al, byte ptr [ecx+0x40]` — which is not in the walk's accepted set
`55 53 56 57 8B 83 81 6A 68 51 52 50 80`. This is trap 2's second cause, and `0x8A` belongs on that
list.

**Trap 14, four times, and three of them were already-answered questions.**
`0x669550` was already `TokenToFixedPoint` with the thousandths rule spelled out.
`CEffect::TakeScalarValue` (`0x15FF0`) already described slot 7 — and is literally `CTrigger`'s own
slot 7, the same folded stub. `CTechnologyStatus +0x218` was already `level_by_technology`, "ints
indexed by a technology's index (`CTechnology +0x244`)", which is exactly the index chain
`CTechnologyTrigger::Evaluate` walks. `CSubUnitDataBase +0x78` was already `hq_brigade`.
Separately, `CCountry +0xBCC` is named `manpower` on the **C++** side only
(`BiceLib/Hooks/Tooltips/ManpowerText.cpp` patches `add [esi+0xBCC], eax`) and was missing from
`project.json` — the two halves of the fact base drifting again.

**Trap 1, in the record's prose.** One `project.json` comment writes
`CCountryDataBase::CCountryDataBase` as `0x2024D0`; the address record says `0x24D0`, which is
right. Rva `0x2024D0` decodes to garbage.

**Trap 12.** The `+0x18`/`+0x19` reader scan and the `scope->+0x40` scan both follow `mov reg, reg`
and `mov reg, [ebp+8]` and nothing harder, so both reader lists are floors, not ceilings.

## 8. What is not established

- **Which end of `surrender_progress`'s 0..1000 range means "about to surrender".** The scale is
  read off the clamp; the direction is not. `0xFCC60`, the divisor inside
  `CCountry::GetSurrenderProgress`, is unnamed and is on the frontier.
- **The four `total_*` war-statistics fields** `CCountry +0x1070`/`+0x1074`/`+0x1078`/`+0x107C`. The
  bodies are certain and the operand is divided by 1000, so the fields are whole numbers; the
  *names* rest only on the keyword of their single reader and on their sitting in a run immediately
  below the three `*_battles_fought` counters the savegame names. No save key is written for any of
  them.
- **Why `lost_IC` is thousandths when `total_ic` is whole IC.** `CCountry +0x1158` is compared

## The six resource triggers, and the exile question

Wave 13 agent B, 2026-10-05. Addresses are **rvas** against `0x400000`.

`money`, `energy`, `metal`, `rare_materials`, `crude_oil`, `supplies` - one body repeated six times,
`0x61` bytes and 32 instructions each, at rvas `0x5F5E70`, `0x5F61E0`, `0x5F6550`, `0x5F68C0`,
`0x5F6C30`, `0x5F6FA0`. Two `ret 4` each (the two arms of one branch - no cold path), thirteen `int3`
before and fifteen after, except `0x5F5E70` which has four before.

**The `0x370` stride is real and is not a fold**, and the vftable settles it for free rather than for
two of the six: the six entries are slot 6 of six *distinct* tables at VA `0x15F9034`, `0x15F9068`,
`0x15F909C`, `0x15F90D0`, `0x15F9104`, `0x15F9138` - `0x34` apart, in the **same order** as the
bodies. Six distinct addresses, each held by exactly one table. `vtable.py --holding` on each returns
one holder.

### The branch is `CCountry::GetPool` inlined - and the answer

**The branch is not trigger machinery.** `CCountry::GetPool` (rva `0xF4DE0`, already recorded and
`confirmed`) is ten instructions and is *this branch, instruction for instruction*: the same
`cmp byte ptr [reg+0x95],0; je; lea reg+0x9F8; jmp; call 0x42F100; add eax,0x15C`. It is the game's
single goods-pool accessor, and it is inlined at **40 sites** across the image - a scan for
`lea reg,[reg+0x9F8]` with a `+0x95` byte compare within `0x20` bytes before and an `add eax,0x15C`
within `0x20` after finds 40 of 71 `+0x9F8` leas, and they include `CCountry::UpdateIC`,
`CCountry::GetResourceLimitedIC`, `CCountry::ConsumeIcResources`, `CCountry::GetAvailableIC`,
`CDistributeSupply::Distribute`, `CUnit::ConsumeSuppliesAndFuel`, `CConvoy::RunDelivery` and
`CChangeLawCommand::Execute`.

So, to the question - **does a government in exile read its host's goods, or its own, and which
province's?**

- **Its own.** `CCountry +0x9F8 pool_in_exile`. A `money` or `supplies` test on a government in exile
  never sees its host's stockpile, and this is not a trigger-side quirk: *everything* in the
  production and supply code reads the exile's own pool too, through the same inlined accessor.
- **Every other country reads the pool physically held on a province** - `CMapProvince +0x15C pool` -
  and the province is the one `CCountry +0xE24 acting_capital_province_id` names. The **acting**
  capital, not the declared one at `+0xE20`; `CCountry.hpp` records that the acting capital is what
  falls back when the declared capital is lost.
- `CCountry::GetActingCapitalLocation` re-read to its `ret` at `0x2F1AD`:
  `g_CCurrentGameState (0x1A89790) ->provinces (+0xB8C) [this->+0xE24]`, a `CMapProvince*`.
  VA `0x42F100`, rva `0x2F100`.

**Two corrections, and the second is to the brief that commissioned this.** The earlier plan's
"reaches the goods pool through a getter at `0x12F100`" was trap 1 - the right function is
`CCountry::GetActingCapitalLocation`, rva `0x2F100`. But the replacement reading - "so the branch does
**not** select a different pool: it looks up an acting capital" - is also not right. **The branch does
select a different pool**, and the acting-capital lookup is only what the non-exile arm needs in order
to find the province that holds it. The earlier agent's instinct about a pool branch was correct; its
address was not.

**And trap 14 again, in its most expensive form: every fact needed to answer the question was already
in the fact base** - `CCountry +0x95 government_in_exile`, `+0x9F8 pool_in_exile`,
`+0xE24 acting_capital_province_id`, `CMapProvince +0x15C pool`, all seven `CGoodsPool` fields, and
`CCountry::GetPool` itself with a comment that says in plain words "answers the capital province's
pool, or the country's own pool at `+0x9F8` when the country is a government in exile". The question
was open because nothing connected the trigger to `GetPool`. No struct field is recorded from this
reading for exactly that reason.

### Scale, and two things a mod author would get wrong

All six derive from `CValueTrigger`; slot 7 is `CValueTrigger::TakeScalarValue` (`0x5D13E0`), which
puts `TokenToFixedPoint(text)` in `+0x40` in **thousandths**, and `CGoodsPool`'s fields are
thousandths. Thousandths both sides, no scaling in the body, so `money = 0.5` really is half a unit
and the decimal survives. Slot 11 is `CTrigger::CountEvaluation` (`0x5D06C0`), so each counts as one
condition in a tooltip.

- **The effect side is integer-only.** All seven `*PoolEffect` classes (`CEnergyPoolEffect`,
  `CFuelPoolEffect`, `CMetalPoolEffect`, `CMoneyPoolEffect`, `COilPoolEffect`,
  `CRareMaterialsPoolEffect`, `CSuppliesPoolEffect`) are `CIntEffect` heirs, whose slot 7 is
  `atoi(text) * 1000`. So **`money = 0.5` as a *trigger* means half a unit and as an *effect* means
  zero** - the same text, two scales, and nothing in the script shows the difference.
- **`CGoodsPool` has seven goods and only six have a trigger: there is no `fuel` trigger.** The RTTI
  export has no `CFuelTrigger`, while `CFuelPoolEffect` exists. A script can set a country's fuel and
  cannot test it. *The control for that negative:* the same name query over the RTTI export finds all
  six of the others and finds `CFuelPoolEffect` on the effect side. If someone wants to be sure,
  `FINDINGS-script.md`'s 152-keyword table is the place a `fuel` keyword handled by some other class
  would show up.

### One dead store, and what was not chased

`mov [esp+8], scope->country_tag (+0x10)` at `0x5F5E8B` (and the same instruction in all six) is never
read - the remnant of a `CCountryTag` temporary the compiler optimised into the direct database index.
Harmless; noted so the next reader does not look for its consumer.

**The gap this leaves, named:** nobody looked for a *writer* that keeps `pool_in_exile` in step with
the host's pool. If one existed, the distinction would be invisible in play even though the read paths
are genuinely separate. That is the one way the mod-facing conclusion above could be true of the bytes
and false of the game, and it is the cheapest next step - the savegame is the oracle, since a
government-in-exile country's `pool` block is plain text.
